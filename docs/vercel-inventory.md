# Загрузка инвентаря на Vercel

Steam может возвращать HTTP 429 для исходящего IP сервера. Локальная разработка и Vercel используют разные исходящие IP. Кэш снижает число обращений, но не снимает ограничение, которое Steam уже применил к IP.

## Что работает в коде

- Успешный ответ Steam кэшируется на 120 секунд с момента завершения загрузки. Ключ состоит из SteamID64 и игры; смена валюты использует тот же инвентарь.
- Одновременные запросы одного инвентаря объединяются внутри процесса. Разные загрузки Steam не запускаются одновременно в одном процессе.
- HTTP 429 включает паузу для всех профилей и игр. Учитывается `Retry-After` в секундах или формате HTTP-даты. Если Steam не прислал срок, используется пауза 60 секунд; повторные ограничения увеличивают её до 15 минут. Это срок следующей попытки, а не обещание разблокировки Steam.
- API возвращает срок в `Retry-After` и `error.retryAfterSeconds`. Браузер блокирует повторную отправку, переключение игры и обновление до окончания паузы. Автоматических повторных запросов нет.
- Если подключён Redis, экземпляры Functions используют общий кэш, общую паузу и атомарную блокировку загрузки Steam. При недоступности настроенного Redis новые обращения к Steam останавливаются.
- Записи `inventory_request_failed` в логах содержат код ошибки, статус, срок следующей попытки, регион и режим подключения. Trade URL, токены и реквизиты выплат в них не пишутся.

## 1. Общий кэш для Vercel

1. В проекте Vercel подключить Upstash Redis через Marketplace / Storage.
2. Проверить серверные переменные `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN` для нужного окружения. Поддерживаются также `KV_REST_API_URL` и `KV_REST_API_TOKEN`.
3. Пересобрать и опубликовать проект (Redeploy).
4. В Runtime Logs открыть `/api/inventory` и проверить `inventory_request_failed`. `STEAM_RATE_LIMIT` означает HTTP 429 от Steam; `CACHE_UNAVAILABLE` — ошибку конфигурации или доступности Redis; `INVENTORY_BUSY` — уже занятую очередь загрузки.

Без этих переменных используется только кэш и пауза отдельного процесса. Общий кэш не включается автоматически.

Токен Redis должен поддерживать запись и команды `GET`, `SET`, `EVAL`. У него не должно быть префикса `NEXT_PUBLIC_`. Ключи и значения не нужно вставлять в чат или Git.

## 2. Если Steam продолжает ограничивать IP Vercel

Запустить этот же Next.js-проект на отдельном сервере с HTTPS. Сначала проверить один запрос с этого сервера: постоянный IP сам по себе не гарантирует доступ к Steam. Учитывать паузы и ограничения Steam; ротация адресов не используется.

На отдельном сервере:

```env
INVENTORY_API_TOKEN=<секрет для доступа к API>
```

Оставить `INVENTORY_BACKEND_URL` и `INVENTORY_BACKEND_TOKEN` пустыми. Сервер запускается обычными `npm ci`, `npm run build`, `npm run start` и публикуется за HTTPS reverse proxy. Токен `INVENTORY_API_TOKEN` закрывает `/api/inventory` от запросов без `Authorization: Bearer …`.

На Vercel:

```env
INVENTORY_BACKEND_URL=https://<домен отдельного сервера>/api/inventory
INVENTORY_BACKEND_TOKEN=<тот же секрет>
```

Оставить `INVENTORY_API_TOKEN` на Vercel пустым, затем выполнить Redeploy. Запросы инвентаря будут идти через отдельный сервер. При его ошибке запрос не переключается обратно на IP Vercel.

На отдельный сервер передаются только `steamId64`, `appId`, `currency`. Steam Trade token и платёжные реквизиты не передаются. Сервер может использовать Redis из первого варианта или собственный процессный кэш.

## Проверка

`npm run test:inventory` проверяет паузы, HTTP-заголовки, общий кэш, блокировку одновременных загрузок и защищённое перенаправление. `python scripts/check_inventory.py http://localhost:3000` проверяет браузерные сценарии; ответы Steam подменяются только внутри теста.

Источник настройки: [Vercel Storage](https://vercel.com/docs/storage), [Upstash REST API](https://upstash.com/docs/redis/features/restapi).
